# slop-spine v1.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make slop-spine look and feel like its sibling apps, and finish the rig-mode work v1.1 planned but did not run.

**Architecture:** Seven tasks on a complete v1.1. Tasks 17-20 adopt slop-animator's existing design system and conventions rather than inventing any; Tasks 21-22 are carried verbatim from the v1.1 plan, where they were written and never executed.

**Spec:** `docs/superpowers/specs/2026-08-22-slop-spine-design.md`

## Why this exists

Three of these come from a single question: *we are copying functionality from slop-animator, so why not the UI too?*

The answer split three ways, and the plan follows it:

- **Components: no.** `LayerList.svelte` is 1,033 lines importing `anim/row-layout`, `anim/active-row` and `anim/document` — it is the left edge of a dope sheet, not a layer list. `ToolOptions.svelte` imports `rowAdmitsTransform`/`whyNotEditable`. Their `Canvas.svelte` is 2,282 lines to our ~350. Gutting them would leave less than we wrote fresh, and editing copied files breaks the byte-identical `diff` check that has caught real problems twice.
- **The design system: yes, near-verbatim.** slop-animator's `app.css` is a full token palette with a `.dark` variant, range-input styling, `:focus-visible` conventions and iPad viewport rules. Ours is one line: `@import "tailwindcss";`. It is CSS, so it copies.
- **Conventions: yes, and cheap.** Both sibling apps bind `b`/`e`/`g` for brush/eraser/fill. slop-spine binds neither, so muscle memory built in two apps does not transfer to the third.

Tasks 21-22 close the rig-mode gaps found by using the app: the overlay hides the one failure the weighting is known to have, and one global density cannot serve a character with both a torso and hair strands.

## Global Constraints

Same as v1.1, plus:

- **Ethos: rough, indie, deliberately imperfect.** Ship the dumb version that mostly works. If a task starts feeling thorough, that is a smell.
- **Adopt, do not invent.** Where slop-animator has a class string, token, icon choice or keybinding, copy that exact value. The point of these tasks is that the three apps agree, so a "better" variant is a defect.
- **Dark stays the default.** slop-animator's tokens are light-first with a `.dark` override; slop-spine keeps its current dark appearance by applying `.dark` at startup. Adopting the tokens is what makes a future light mode or theme toggle trivial — it is explicitly not this plan's job.
- **Test only what cannot be eyeballed.** Task 16 is the only one adding a test. The rest are UI, verified by driving real Chrome, with the controller judging screenshots.
- **Every task runs `npm test` AND `npm run check` before committing, both clean.** The 47 existing tests must still pass.
- Strict `tsconfig`; **runes mode enforced**.
- **`layer.canvas` must stay transparent where nothing is drawn** — export trims on alpha. `verify.html`'s guard fires on any region whose trim equals the full canvas, and has been seen to fire.
- **`revision` is monotonic** — every pixel-restore path bumps it forward, never restoring an old value, or `deriveSlot`'s cache ABAs onto a stale mesh.

- [ ] **Step 3: Replace every `neutral-*` with a token**

Our components carry 62 hardcoded `neutral-*` classes across 8 values. Map them:

| ours | token class |
|---|---|
| `neutral-950` | `canvas-bg` |

Where a `neutral-800` is ambiguous, decide by role: a hover affordance is `surface-hover`, a persistent selected state is `surface-active`. Say in your report if any usage resisted the mapping.

## Task 21: The rig overlay shows the whole character

**Files:** Modify `src/lib/Canvas.svelte`, `src/lib/RigOverlay.ts`

`Canvas.svelte` currently derives and draws the mesh for **only the selected layer's slot**. Every
other part of the character shows no mesh at all.

That is not merely inconvenient — **it hides the one failure mode the weighting is known to have.**
The spec accepts that Euclidean distance-to-segment bleeds across spatial gaps (an arm hanging beside
a hip picks up hip weight) and names geodesic distance as the deferred fix. Bleed is a relationship
*between two parts*, so it is invisible while you can see one part's mesh at a time. Rigging is
inherently about how parts meet; the overlay should show that.

- [ ] **Step 1: Draw every visible layer's mesh**

Loop visible layers, `deriveSlot` each, draw all their triangles dimmed; draw the selected layer's
mesh at full strength on top so it stays legible.

`deriveSlot` is memoised per slot on `(revision, density, boneSignature)`, so after the first frame
this costs a cache hit per layer. Do not add batching or throttling until it visibly stutters.

- [ ] **Step 2: Weight tint across every slot bound to the selected bone**

Today the tint is scoped to the selected layer. Tint **every** slot that binds the selected bone.
This is the step that makes bleed visible: select a hip bone and any weight it is stealing from the
arm lights up in the arm's mesh, in place, where you can see it and fix it upstream by moving a bone
or adjusting the bind.

- [ ] **Step 3: Verify in real Chrome**

Two overlapping layers bound to different bones. Show that both meshes render, that selecting a bone
tints vertices in every slot bound to it, and — ideally — capture a case where a bone tints vertices
in a part it should not influence. That screenshot is the argument for geodesic when someone
eventually wants it.

- [ ] **Step 4: Commit**

```bash
git add -A && git commit -m "feat: rig overlay shows all meshes and cross-slot weight tint"
```

## Task 22: Per-slot mesh density, with the global value as the default

**Files:** Modify `src/rig/document.ts`, `src/rig/derive.ts`, `src/lib/RigPanel.svelte`, `src/persist/project-file.ts`

**Depends on Task 21** — a per-part control is hard to judge while you can only see one part's mesh.

The spec deferred this: *"no per-slot mesh params until one character needs them."* The first real
character needs them, and the reference rig has needed them all along.

Measured from the hand-rigged `sloppets/spine/test-char/char.json`, density varies **16× across
parts** — Mouth 652 px/vertex, Arm b 1,970, Eyes 2,477, Head 5,266, Body 10,586. The pattern tracks
**how much a part deforms**, not how big it is: the mouth is finely meshed because it is sculpted for
visemes, the body is nearly rigid and barely needs vertices, arms bend at one joint and sit between.

One global value cannot express that. Too coarse and thin parts collapse (Task 7's render: a 300×80
arm tapered to a wedge at density 48). Fine enough for hair and the torso gets hundreds of useless
vertices, every one of which is re-weighted on each bone drag.

- [ ] **Step 1: Add the optional override**

`density?: number` on `Slot` in `src/rig/document.ts`. Optional, so absent means "use the document
default" and every existing project file loads unchanged.

- [ ] **Step 2: Effective density in the derivation**

`const density = slot.density ?? doc.density;` — and it must go into the **mesh half** of the cache
key in `src/rig/derive.ts`, which is currently `${layer.revision}|${doc.density}`. Get this wrong and
changing a slot's density silently returns the old cached mesh.

- [ ] **Step 3: RigPanel shows the selected slot's effective value**

The existing density slider becomes per-slot: it shows `slot.density ?? doc.density`, and moving it
sets the override on that slot. Add a small "reset to default" affordance so an override can be
cleared back to inheriting.

Keep the document-level default settable too — it is what new layers start from.

- [ ] **Step 4: Persist it**

Carry `density` through `DocumentJson`'s slot entries in `src/persist/project-file.ts`. Absent stays
absent; do not write `undefined` into the JSON.

- [ ] **Step 5: Verify in real Chrome**

Two layers of very different thickness — a thick torso and a thin strand. Show that a per-slot
density change regenerates **only that slot's** mesh (vertex count changes for it, unchanged for the
other), that it survives a save/load round-trip, and that clearing the override returns it to the
document default.

- [ ] **Step 6: Commit**

```bash
git add -A && git commit -m "feat: per-slot mesh density overriding the document default"
```

## Self-review notes

**Ordering.** 17 before 18 (icons need the tokens) and before 20 (the popup needs `.curve-popup`). 21 before 22 (per-part density is hard to judge while you can see one part's mesh). 16 and 19 are independent.

**Carried forward.** Tasks 21 and 22 are verbatim from the v1.1 plan, where they were written and never executed — v1.1 shipped Tasks 13-15 only.

**Deliberately excluded.** slop-paint's layer groups/nesting (a feature, not a convention, and the rigging workflow has not asked for it), a light/dark toggle (the tokens make it trivial; building it is not this plan's job), and slop-animator's timeline-coupled components.

**Known risk.** Task 17 touches every component in the app, and its failure mode is aesthetic rather than functional — `npm run check` will not catch a wrong token. The controller judges the screenshots, and a wrong mapping is one string to change.
