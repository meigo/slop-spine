Ruling: CONFLICT 2 — resolved Task 15's open question myself instead of spending a task round-trip.
`opacity` is honoured by the renderer and persisted, but absent from `bundle.ts`, so it is view-only
and silently fails to reach the export. Fix by emitting **Spine slot alpha** (`"color": "ffffff"+aa`,
omitted at full opacity) rather than baking alpha into the exported PNG — baking is destructive and
would force re-exporting artwork on every opacity change, whereas slot alpha is what the runtime
already understands and the reference rig's omission of the field confirms the default is opaque
white. Adds `src/export/spine-json.ts` to Task 15's owned files. Cost if wrong: three lines in the
writer that a character at full opacity never emits.

## v1.1 whole-branch review (opus) — findings must be addressed

Ruling: FIX F1 — layer.visible must reach the export. Seventh instance of this project's signature
  bug, and v1.1 created the inconsistency: opacity now exports as slot alpha while visible does not,
  so two adjacent controls that render identically (opacity 0 vs hidden) export to opposite results.
  Emit `attachment: null` for a hidden layer rather than folding it into alpha 0. Reason: null
  attachment is what "hidden" means in Spine, and it leaves the slot keyable in the editor handoff,
  so a hidden construction layer can be toggled back on there without re-exporting. Deliberate
  tradeoff: a hidden layer still consumes atlas space. Cost if wrong: wasted atlas room for hidden
  layers, and the editor shows an empty slot rather than no slot.
Ruling: FIX F2 — call history.clear() in loadDocument. History.clear() already exists and is called
  from nowhere. One line, no import cycle.
Ruling: FIX F3 by making layer delete UNDOABLE, not by adding a confirm. Two reasons. First,
  consistency: the Clear button directly beside it is undoable, and Task 15's own brief refused a
  confirm dialog for Clear on the grounds that "undo is the safety net" — having the MORE destructive
  action be the LESS recoverable one is backwards. Second, and the real problem: a confirm would
  leave the stack lying. Today the strokes of a deleted layer remain on the stack and no-op, so
  Cmd+Z gives silent nothings and then starts undoing other layers' work. Re-inserting the layer
  restores the stack's meaning. The layer's canvas is already retained by the command closure, so
  the pixels come back for free. Cost if wrong: ~15 lines, and delete becomes as reversible as clear.
Ruling: PARK the papercut where focus in the opacity slider blocks Cmd+Z (the keydown guard skips
  INPUT elements, which now includes range sliders). The toolbar button still works, and the guard is
  right for the rename field. Worth knowing, not worth code.
Deferred-minor triage from the review: #1 no-op fill pushing 32MB — LATER (real mechanism: a stray
  fill click can evict genuine stroke history from the 256MB budget). #2-#5 — NEVER.
Final fix wave: all 3 addressed (commits dd4b6fb..9cc9340), scoped re-review clean.
Ruling: SURFACE, do not fix now — the re-review found NEW breakage my F3 fix introduced. Delete-undo
  captures array indices at delete time and trusts them at undo time, but reorderLayer mutates
  doc.layers outside history (never asked to be undoable). Sequence delete B -> drag-reorder C ->
  undo splices B at a stale index, silently producing wrong doc.layers order — which is exactly what

  final review is precisely how regressions land. Concrete fix for v1.2: capture the PRECEDING

  is gone). ~3 lines, removes the staleness class entirely.
